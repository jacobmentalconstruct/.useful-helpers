01Executive verdict

Overall classification

CONDITIONALLY RELEASE READY

The product is real and it works. I installed the sealed artifact on native Linux under three CPython versions and completed the entire consumer acceptance walk — attach, blank state, observe, orient, drill, preview, approve, apply, independently-measured changed paths, receipt visibility, post-apply awareness, compatible update with UUID preserved, clean uninstall with target files intact. That is the core P8 claim, and it reproduces outside the project's own harness.

Three uncaught exceptions stand between this and unconditional readiness, all reachable by ordinary use, all of which break the CLI's own JSON contract by emitting a Python traceback and nothing on stdout. One of them — replacing a directory with a file of the same name — permanently breaks substrate refresh for that target, which disables orientation and the whole governed mutation loop, with no recovery path short of deleting the state database.

T8 / PARKED is justified as a construction disposition — the declared evidence exists, was produced from a clean tree at the current source digest, and was independently re-run by the project's reviewer. It is not justified as a claim that the product degrades truthfully under adverse conditions: P7's "degrade usefully" and P6's "same authority" are supported with real caveats, and one carried finding (C3, MCP client conformance) was discharged by redefinition rather than by evidence.

Most important caveat: the project's discrimination witnesses — the machinery meant to prove the gates can tell success from failure — are, in T2 through T6 and T8, string mutations checked by string assertions. I sabotaged mutation.py to record verification as "passed" and to fabricate the changed-path measurement, and the T5 gate's discrimination_witness check still returned PASS. The real discriminating power lives in the pytest suites, which did catch it. T7 is the exception: its _executed_mutations genuinely patches live code and re-runs known-answer classification.

Would I release this exact state?

To a small group of technical early testers who are told the limitations: yes. To anyone else: not until F-01 and F-02 are fixed. Neither is deep; both are a few lines. Nothing found is unsafe, nothing loses user data, nothing escapes containment, and nothing reports a change that did not happen.

02The project in plain English

Sidecar Workbench is a self-contained instrument you attach to one directory. It installs itself into that directory as a hidden .sidecar/ folder, watches what is there, records durable evidence about it in SQLite, and lets a human or an agent make governed file changes through a single control plane that leaves receipts.

What gets installed

Running python -m factory attach /path/to/target copies three directories — bin/, core/, tools/ — into <target>/.sidecar/, creates state/ and logs/, writes an instance.json holding a UUID and the literal relation "..", and bootstraps a SQLite database. Nothing is written anywhere else on the machine. There is no registry, no home-directory config, no .gitignore dropped into the target. The instrument knows where it lives only structurally: it resolves its target by walking .. from itself, which is why you can rename or move the whole folder and it still works.

What it observes and derives

Nothing happens automatically. substrate refresh is an explicit act that walks the target (skipping .sidecar/), records one resource per file and directory, hashes the ones worth hashing, and writes content-addressed evidence plus deterministic observations. From those it derives a small number of hedged claims: this target has text-like files; this target has software-project signals; this target contains weak material we only saw the metadata of. Every claim is linked by typed provenance edges (derived_from, supported_by, concerns, version_of) back to the observations and evidence that support it, and substrate trace will walk that graph for you.

awareness refresh then builds a compact, immutable revision over the latest coherent substrate basis: a domain profile, a handful of findings, and — this is the part that is genuinely well done — explicit limitations and unknowns. A directory nobody has observed reports unknown_unobserved with freshness unknown. A directory observed and found empty reports observed_empty. Those are different states and the product never conflates them.

What it transforms, and what stops it

Exactly one thing can change a target: writing a file. And it can only do so through a four-step loop. mutation preview-write records the proposed change, the payload digest, the awareness revision it was reviewed against, and a signature of the whole target. mutation approve binds to that exact preview digest. mutation apply refuses — before launching any process — if the approval is missing, if the caller-named preview does not match, if the target has changed since review, or if the awareness basis has moved. If it proceeds, it routes through the ordinary governed host, then independently snapshots the target before and after and reports which paths actually changed, rather than believing the tool's own success message. Verification is recorded honestly as unavailable, because there is no target-native check to run; the product does not invent a PASS.

Who talks to it

A human uses the CLI: python .sidecar/bin/sidecar.py status and about fifty subcommands under it, all of which emit JSON on stdout. An agent uses the same binary in MCP mode (sidecar mcp), a line-delimited JSON-RPC server over stdio that advertises 21 tools — 16 projections of the product's own read and mutation surfaces plus the 5 manifest tools. Both entrances converge on the same ControlPlane, the same SQLite file, and the same receipts; I confirmed a receipt created through MCP appears verbatim in the CLI's receipt list.

What makes it distinctive

Three things, and they are the reason this is worth taking seriously. First, the epistemic separation is real: operational receipts, App Journal work memory, epistemic evidence, and awareness projections live in different tables with different owners and different meanings, and the code genuinely does not collapse them. Second, unobserved means unknown: the product distinguishes "I looked and found nothing" from "I never looked", which almost nothing does. Third, measured reality outranks self-report: after a write, it goes and looks.

The mutation path, and where it refuses

Verified by execution. preview-write first requires that current awareness reports freshness == "current"; on a stale basis it refuses with "current awareness is not fresh enough to preview mutation". apply then checks, in order: approval exists, caller's preview matches the approval, approval digest still matches the stored preview, live target signature equals the reviewed one, and current awareness id, basis signature and freshness all match. I confirmed each refusal is a durable mutation_records row with measurement.source = "not_launched", and that replaying a consumed approval is blocked by stale_target because the successful write changes the file's mtime, which is part of the signature.

The failure path that matters most

I injected a SQLite trigger that aborts every UPDATE on operation_receipts, then applied an approved mutation. The child process ran and did write the file. What the product reported:

status            failed
refusal_code      receipt_persistence_failed
receipt_id        null
post_awareness_id null
measurement       {"changed_paths": ["doc.txt"], "source": "independent_target_snapshot"}
receipts table    one row, status='started', completed_at=NULL, artifact_id=NULL

This is the correct direction on every axis. It did not claim success. It did not hide the physical change — the independent measurement still names the changed path. It left an incomplete receipt rather than a false one. The only residue is that nothing ever reconciles that orphaned started receipt, which I record as informational rather than a defect.

The agent entrance

I wrote an independent MCP client that sends only what the 2024-11-05 spec defines and used nothing from the project's fixtures. Handshake, tools/list (21 tools), and every read projection worked. What did not work is covered in F-06.

Install, update, remove

attach refuses if .sidecar already exists, and removes a partial footprint if anything in the sequence throws. update stages fresh payload into .sidecar/.update-<token>/, renames each of bin, core and tools aside as .old-<name>-<token>, copies the new payload in, then deletes both. uninstall is a single rmtree of .sidecar; I confirmed target-owned files survive it byte-for-byte. Behaviour under interruption is F-07.

How authority actually works

Three levels — observe < sandbox < apply — declared per manifest, compared against a caller-supplied level, checked before the child process starts, and recorded on the receipt whether the call succeeds or is refused. It works exactly as designed.

Read this correctly

Authority here is attribution and intent, not access control. The CLI accepts --authority apply from anyone who can run the binary; there is no token, no prompt, no credential. That is a coherent choice for a single-user local instrument, and the Charter never claims otherwise. But a reader who sees "governed mutation" and "authority" should not infer that Sidecar restricts what a local actor can do. It restricts what Sidecar does, and it leaves a receipt for each one.

Provenance you can actually follow

Every awareness finding carries source handles; awareness drill <item> resolves them through substrate.trace into observations, evidence and resources. Every claim records its derivation_method (deterministic.domain_signals, deterministic.resource_count, deterministic.suffix_classification) and a confidence. Every mutation record links preview, approval, verification, receipt, artifact, both awareness revisions, and any journal entry. A user can answer "what was observed, what was derived, from what, when" for any statement the product makes. This is the strongest part of the design.

Did later work quietly invalidate earlier parked work?

No, and this is worth stating plainly because it is the most common way a tranche project rots. Two specific checks:

  • T6 narrowed the parked T3 and T5 gates to permit the new MCP surface. I read the exemptions: they are now explicit allowlist constants (POST_T3_MCP_ALLOWED_FILES, POST_T5_MCP_ALLOWED_FILES) naming exact files, not open-ended term removals. The parked invariants — substrate and storage must not grow MCP ownership; mutation and control must not grow MCP behaviour — still hold.

The T3 gate was left untouched and still passes, and the T3-owned tables and trace semantics are unchanged. The rewrite added behaviour above the parked contract rather than altering it.

The cumulative gate discipline — re-running T7 down to T0 at each submission — is real and it worked. Eight fresh receipts back the terminal park.

08Bugs and correctness findings

F-01Replacing a directory with a file of the same name permanently breaks substrate refreshHIGH

The resources table declares both handle and path as UNIQUE, and resource_id is the handle. The handle encodes kind — a directory foo becomes path:foo/, a file foo becomes path:foo — but path is 'foo' for both. The ON CONFLICT clause in substrate.refresh targets resource_id only, so when a name changes kind the insert collides on path and nothing handles it.

Evidence
product/core/storage.py:127-136 (schema), product/core/substrate.py:834-861 (upsert), substrate.py:140-149 (_resource_handle)
Reproduction
mkdir t/thing; echo x > t/thing/inner.txt, attach, substrate refresh, then rm -rf t/thing; echo x > t/thing, substrate refresh. Also reproduces file to directory.
Consequence
sqlite3.IntegrityError: UNIQUE constraint failed: resources.path, uncaught, traceback on stderr, nothing on stdout, exit 1. Permanent — every later refresh fails identically. Awareness therefore never leaves stale, and because preview-write requires fresh awareness, the entire governed mutation loop is dead for that target. The only recoveries are deleting the state database (losing all App Journal entries and receipts) or hand-editing SQL.
Mitigating
Awareness stays honest throughout — it reports freshness: stale and does not fabricate. Nothing is lost or corrupted; the instrument simply stops being able to see.
Why tests missed it
No fixture in any of the nine test files changes a path's kind between refreshes. The T7 suite exercises many target shapes but always builds each one once.
F-02mutation apply with an unknown approval id crashes instead of refusingHIGH

_refusal() writes a mutation_records row whose preview_id column has a foreign key to mutation_previews. On the approval_not_found path it passes the caller's unknown identifier straight into that column, so with PRAGMA foreign_keys = ON the insert violates the constraint.

Evidence
product/core/mutation.py:239-247 and mutation.py:629-660; FK declared at storage.py:299
Reproduction
sidecar mutation apply mutation:approval:doesnotexist
Consequence
sqlite3.IntegrityError: FOREIGN KEY constraint failed, uncaught. The CLI emits zero bytes on stdout, breaking the contract that every response is JSON. Any agent or script parsing stdout gets a JSONDecodeError instead of a refusal it can reason about. A typo, a stale id from an earlier session, or an id copied from a different instance all trigger it.
Divergence
The same call through MCP returns a structured -32000 error, because mcp._handle_line has a broad except Exception. Identical defect, two different behaviours — directly relevant to the parity claim.
Why tests missed it
The test that claims to cover this passes a valid preview id as the approval id. tests/test_t5_governed_mutation.py:263 calls self.mutation_refusal(target, "apply", preview["preview_id"]). Because that identifier does exist in mutation_previews, the FK is satisfied and the refusal path works. The test named test_apply_without_approval_and_stale_apply_refuse_before_launch has never exercised a genuinely unknown identifier.

09Architectural frailties

Structural risks, distinct from the defects above.

Resource identity conflates address and kind

The root cause of F-01 is not the missing exception handler; it is that resource_id == handle and the handle encodes kind, while path is separately unique. A resource's identity should be its path; its kind should be a mutable attribute of the current version. As written, a name that changes kind is two conflicting identities for one address. Fixing the crash without fixing the model leaves the same tension for any future kind (symlink, socket, junction).

The three-caller scan is the hottest path and it is unmemoised

_resource_records() walks and hashes the whole target. It is called by substrate.refresh, by target_signature, and therefore by _freshness — which runs once per awareness row read. That means a read-only listing performs N full target scans. It is also where F-03 lives. One function, three very different callers, no caching, no error tolerance.

Truthfulness under uncertainty — the honest scorecard

  • Distinguishes observation from inference: yes. Observations are typed (file_hash, file_metadata, resource_seen, domain_signal, resource_inventory); claims carry a derivation_method and a confidence.
  • Distinguishes inference from uncertainty: yes. Every awareness revision carries limitations and unknowns arrays, and a weak-material claim states that content changes are detected only through size and mtime.
  • Refuses unsupported interpretation: yes. Five unknown-extension files produce zero claims and generic_observed. It does not guess.

15Security, boundaries and failure modes

Judged against the documented threat model: a single-user local instrument attached to a directory the user already controls. There is no multi-user story, no network surface, no authentication, and none is claimed.

Containment — the strongest result in the review

16 escape attempts, 16 refusals, nothing written outside the target. Containment is real-path based and symlink-aware, not lexical: resolve_path calls .resolve() before the boundary check, so a symlink pointing out of the target is caught (verified for both a symlinked file and a symlinked directory, read and write). Absolute paths are rejected outright, NUL bytes are rejected, and target-scoped tools are additionally forbidden from touching the instrument's own subtree. The walking tools (inventory, search_text) never follow symlinks and disclose how many they skipped.

Where the boundary actually is

State this plainly to anyone evaluating the product

Sidecar governs its own operations. It does not govern the filesystem, and it cannot. Any local process — including an agent that has been given a shell — can write to the target directly, or run python .sidecar/tools/write_file/tool.py with a crafted stdin, and no receipt will exist. I demonstrated the second. The mechanical tools carry no containment of their own; that is by design (Charter invariant 5 gives containment to the host) and it is what makes them portable. The honest framing is: receipts prove what Sidecar did, not what happened to the directory. The substrate's target signature will notice the change on the next refresh, so out-of-band edits are detectable — just not attributable.

17What went especially well

Product and process separation

The single best decision in the project. 4,378 lines of gates and 4,700 lines of governance prose exist, and not one line of them reaches the runtime. No tranche concept, no gate, no PARKED state, no evidence path appears in product/. The release excludes them by positive selection rather than a growing denylist, and the boundary is checked by AST rather than grep. Many projects with this much process end up shipping it; this one does not.

Containment

Real-path-based, symlink-aware, uniformly applied, and it held against every attack I could construct. The decision to resolve before checking — rather than doing lexical .. stripping — is the correct one and it is rarer than it should be.

The unobserved and empty distinction

A never-observed directory and an observed-empty directory are genuinely different states with different profiles, different freshness, different unknowns. Systems routinely collapse these. This one does not, and the whole epistemic model is better for it.

Honest failure direction

Every failure I injected pushed toward under-claiming. Receipt persistence failure after a real write reports failure while still naming the changed path. Verification with no mechanism available records unavailable, not PASS. Awareness with a broken substrate reports stale rather than guessing. In a product whose entire pitch is truthful instrumentation, the failure modes point the right way — and that is much harder to get right than the success paths.

Genuine adapter removability

MCP is imported in exactly one place, lazily, inside its own subcommand branch. Deleting mcp.py from an installed instrument leaves status, catalog, tool calls, receipts, substrate, awareness and mutation completely intact, and sidecar mcp returns a truthful mcp_unavailable. Removability claims are usually aspirational. This one is verifiable in one rm.

T7's executed discrimination

After three reviewer returns, T7 produced the only gate in the repository that proves its own discriminating power by running mutated code against known answers. It is the template the other eight gates need.

Cumulative gate discipline

Re-running T7 down to T0 at every submission, with fresh receipts cited by run id and SHA-256, is the reason I can say with confidence that later tranches did not quietly invalidate earlier ones. The discipline cost a lot of receipts and it bought a real answer.

The reviews themselves

The external reviews are unusually good. They returned candidates three times in T7 alone, over substantive issues — every real repository classifying as mixed, .git being 80% of the substrate, large files being hashed before being declared metadata-only — rather than style. The carried-findings draft is a model of how to record a disposition for every finding instead of letting them evaporate. The gaps I found are gaps in what those reviews tested, not in their seriousness.

21Final judgment

If this repository were handed to an entirely new maintainer today as the finished prototype, is it sufficiently coherent, truthful, reproducible, understandable, testable, installable, removable and complete to deserve its final parked state?

Yes, with three qualifications.

  1. Two defects must be fixed before anyone outside the project uses it: the resource-kind collision that permanently disables observation (F-01), and the approval-not-found crash whose covering test is a false positive (F-02). Both are small; neither is architectural.
  2. Two claims must be restated to match reality: P6's "same authority" (an MCP client cannot discover or supply it) and P7's "degrade usefully" (which holds across content and not across access).
  3. The gate discrimination witnesses outside T7 must be documented as decorative, or replaced with T7's executed approach, before anyone treats a receipt's "rejected: …" line as assurance.

The strongest aspect

Product and process separation, and the epistemic honesty built on top of it. A project carrying 4,378 lines of gates, 60 journal entries, 250 receipts and 21 external reviews shipped a 5,558-line runtime with zero construction concepts in it — and that runtime distinguishes what it saw from what it inferred from what it does not know, links every claim to its evidence, and points its failure modes toward under-claiming. Those two things together are rare, and they are the reason this prototype is worth continuing.

The weakest aspect

Robustness against the filesystem it is built to instrument. A directory-bound instrument for arbitrary directories crashes on an unreadable file, silently omits an unreadable folder, and permanently breaks when a name changes from a folder to a file. The product reasons carefully about content it cannot understand and not at all about access it does not have. Every one of these is a few lines of exception handling and one schema decision — the gap is narrow, but it sits directly on the product's central promise.

The single most important unresolved issue

F-01 — the resources.path uniqueness collision. It is the only finding that is permanent, that disables the core loop rather than one command, and that has no recovery path a normal user could execute. It also reveals a model problem — identity conflated with kind — rather than just a missing try.

The single most important thing not to disturb

The dependency direction and the mechanical tool contract. MechanicalContext carrying exactly target_root and excluded_roots and rejecting anything else is the hinge the whole architecture turns on. It is what makes the tools portable, the host authoritative, MCP removable, and the release boundary provable. It was the hardest thing T1 fought for, and it has survived seven subsequent tranches unbroken. Anything that puts identity, state, or a projection back into that context undoes more than it looks like it does.

Would I release this exact state?

Not this exact state — but very close to it. Fix F-01 and F-02, widen the CLI's exception tuple, add an onerror handler to the substrate walk, and write the two-page consumer README the reviewer already asked for. That is perhaps a day of work, and none of it touches the architecture. Then release it, with the MCP authority limitation and the state-growth behaviour stated plainly as known limitations rather than discovered by the first person who tries.

On the T8 / PARKED declaration itself

Nothing in this review invalidates it. The tranche produced the evidence it declared, from a clean tree at a source digest that has not drifted, reviewed by someone who re-ran the gate independently and recorded its residual risks honestly. The findings above are things the project's own process was not designed to look for — adversarial filesystem conditions, an external protocol client, and the gates' own discriminating power — rather than things it looked for and got wrong. That is a meaningful distinction, and the project earns it.
